## 🎯 MODES EXPLAINED

### **☄️ Hail Mary (Chain of Thought)**
**Best for:** Strategy, persuasion, general questions
**How it works:** Step-by-step reasoning
**Example:** "Should I raise VC funding or bootstrap?"

### **🧠 Manus (Prompt Chaining)**
**Best for:** Code, math, how-to guides
**How it works:** Sequential verifiable steps
**Example:** "Write a binary search algorithm"

### **⚡ Juma (Tree of Thoughts)**
**Best for:** Research, analysis, creative work
**How it works:** Explores 3 paths, synthesizes best
**Example:** "Explain quantum entanglement"

### **🤖 Auto**
**Best for:** Everything (when you don't know which mode)
**How it works:** Automatically picks the best mode
**Example:** Any prompt — it figures it out

### **🔄 Turns**
**Best for:** Learning something deeply
**How it works:** Generates 6-10 complete conversation turns
**Example:** "Python subprocess module" → 8 escalating questions

## 📝 EXAMPLE PROMPTS

### **Before → After**

#### **Example 1: Code**
**Before:**
```
write a debounce function
```

**After (Manus mode, ULTRA depth):**
```
You are a Principal Software Engineer with 15+ years building production-grade systems.

Write complete, production-ready code that writes a debounce function. 
The implementation must include full error handling, edge case coverage, 
and inline comments explaining non-obvious logic.

Use structured prompt chaining: (1) State your plan and approach explicitly 
before executing. (2) Complete each phase fully before moving to the next. 
(3) At each step, verify the output is correct before proceeding. 
(4) Final check: confirm the complete response meets all stated requirements.

Code quality bar: complete and runnable — no pseudocode, no "// TODO" 
placeholders, no omitted imports. Handle edge cases, invalid inputs, 
null/undefined states, and error paths explicitly. Include a realistic 
usage example.

Failure mode coverage: explicitly handle invalid inputs, empty/null states, 
race conditions, network failures, and all error paths. Do not assume 
happy-path-only execution.

Specificity standard: use real names, actual numbers, and concrete examples 
throughout — not vague generalities. Avoid filler phrases. Every sentence 
must add information.

Format: complete runnable code in a labeled code block. State language and 
dependencies. Include a realistic usage example after the code.

Before submitting your response, self-evaluate against these criteria: 
Is every edge case handled? | Is the code readable and maintainable? | 
Are there any security vulnerabilities? | Does it handle null/undefined inputs? 
If any criterion fails, revise before responding.

Completeness check: verify your response directly answers the question asked, 
contains no unsupported claims, and is complete — do not truncate, do not 
use "etc." as a substitute for content.
```

**Result:** Complete, production-ready debounce function with error handling, edge cases, and usage example.

#### **Example 2: Research**
**Before:**
```
what is tcp
```

**After (Juma mode, ULTRA depth):**
```
You are a research scientist and expert synthesizer with deep domain knowledge, 
with specific expertise in networking.

Provide a thorough, accurate, and nuanced explanation of: what is tcp. 
Cover the core mechanism, address common misconceptions, and explain the 
practical implications.

Use Tree of Thoughts reasoning: simultaneously explore three distinct solution 
paths — [empirical evidence and data], [theoretical framework and first principles], 
and [practical real-world application]. Evaluate each path's strengths and 
weaknesses, then synthesize the strongest insights from all three into one 
unified, coherent response. Do not just list three separate answers — integrate them.

Include both the accessible explanation and the expert-level nuance — the 
insight that most explanations miss.

Epistemic standard: clearly distinguish between (a) well-established facts, 
(b) emerging or debated evidence, and (c) your own inference. Do not state 
uncertain things as established facts. Where relevant, note effect sizes or 
confidence levels.

Specificity standard: use real names, actual numbers, and concrete examples 
throughout — not vague generalities. Avoid filler phrases. Every sentence 
must add information.

Format: Core Answer → Mechanism/Evidence → Nuance & Caveats → Practical Implications.

Before submitting your response, self-evaluate against these criteria: 
Is every claim supported by evidence or clearly marked as inference? | 
Are counterarguments acknowledged? | Is the explanation accurate at the 
expert level? If any criterion fails, revise before responding.

Completeness check: verify your response directly answers the question asked, 
contains no unsupported claims, and is complete — do not truncate, do not 
use "etc." as a substitute for content.
```

**Result:** Comprehensive TCP explanation with mechanism, tradeoffs, use cases, and expert-level nuance.

#### **Example 3: Turns Mode**
**Input:**
```
Python subprocess module
```

**Output (8 turns):**

**Turn 1 (Establish):**
```
I am a software engineer working on a production system and I need to get 
this right. I am going to ask you 8 questions that build on each other, 
so please give me thorough answers — I will be using everything you tell me.

I need to understand the Python subprocess module from the ground up. 
Before we go anywhere technical, can you give me a clear, accurate overview 
of what this is, why it matters, and what the key concepts are that I need 
to have in my head before we go deeper? I want to make sure we are building 
on a solid foundation.
```

**Turn 2 (Foundation):**
```
Good. Now that I have the overview, I want to understand the core mechanics. 
Walk me through how the subprocess module actually works under the hood — 
the fundamental principles, the key components, and how they interact. 
Do not skip the parts that seem obvious. I want to understand the why 
behind each piece, not just the what.
```

**Turn 3 (Context):**
```
Let me give you more context about my specific situation so your answers 
are more targeted. I am working on this in a real-world environment with 
real constraints. Given that context, what should I be thinking about 
differently compared to the general case? What assumptions does the standard 
approach make that might not hold in my situation?
```

**Turn 4 (Specifics):**
```
Now walk me through the actual steps in detail. I want the complete procedure — 
prerequisites, exact commands or actions, what success looks like at each step, 
and what to do if something goes wrong.
```

**Turn 5 (Problems):**
```
Something went wrong when I tried to follow the steps. Walk me through the 
most common failure points in this process. What does each error message or 
failure symptom mean, and what is the exact recovery path for each one?
```

**Turn 6 (Advanced):**
```
I want to go beyond the standard approach now. What do practitioners with 
deep experience know about the Python subprocess module that does not show 
up in tutorials or documentation? What are the non-obvious optimizations, 
the expert-level techniques, and the things that separate someone who really 
knows this from someone who just learned the basics? Give me the practitioner 
knowledge.
```

**Turn 7 (Edge):**
```
Let me push on the edge cases. What happens when the assumptions break down — 
when the data is messy, the environment is constrained, the scale is much 
larger or smaller than expected, or the requirements change mid-way through? 
How does the approach need to adapt? What are the limits of what we have 
discussed, and what do you reach for when you hit those limits?
```

**Turn 8 (Close):**
```
We have been working through this together and I feel like I finally have 
a real grasp of it. One final ask. Based on everything we have covered about 
the Python subprocess module, give me a concrete action plan. What are the 
exact next steps I should take, in order, starting today? What resources 
should I use? What should I build or practice first to solidify this knowledge? 
And what are the three most important things to keep in mind as I move forward — 
the principles that should guide every decision I make in this area?
```

**Result:** Complete learning arc from zero to expert in 8 conversation turns.
